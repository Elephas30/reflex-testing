REFLEX  ·  SYSTEM DESIGN DOCUMENT

How Reflex is structured

A real-time delivery coordination system for Kenyan retailers, replacing WhatsApp-based dispatching. This document covers the service architecture, the order lifecycle, core data, and the four screens a person actually uses.

01Architecture — three independent services

Reflex is deliberately split into three services that don't share code or dependencies. Each is its own repository and can be built, tested, and deployed without touching the others.

SERVICE MAP
reflex-backend
REST API. Owns all state: requests, assignments, QR tokens, tracking codes. In-memory store, deployed on Render.
OWNER: DOMISIANO
reflex-frontend
Web client. Retailer, dispatcher, and rider views, plus the public no-login tracking page. Talks to the backend over HTTP only.
OWNER: GENESIS
reflex-testing
Standalone Node script. Hits the live backend over HTTP to prove edge cases and produce trade-off evidence.
OWNER: MAINA
— all three talk over plain HTTP, never shared code —

This shape is the actual security/trade-off story worth telling the panel: nobody can accidentally break another person's build, and the testing suite is proof the API contract holds even from a completely outside caller — the same as a real client would be.

02Order lifecycle

Every delivery request moves through five stages, each one gated so it can't be skipped or done twice.

STATE FLOW
RECEIVED
retailer creates
ASSIGNED
dispatcher → rider
PICKED UP
rider confirms
OUT FOR DELIVERY
rider en route
DELIVERED
QR scan confirms

The last transition is the one worth designing around: the rider doesn't just tap "delivered" — they scan a QR code the retailer generated for that specific request, and the backend checks the scanned token against the real one before accepting it. A guessed or reused token is rejected; a repeat scan of the correct one is a safe no-op, not a duplicate delivery.

Access control, not just flow control: a rider can only act on a request assigned to them (HTTP 403 otherwise), and a request can't be reassigned once it's already assigned (HTTP 409) — both enforced server-side, not just hidden in the UI.

03Core data

Four things the system tracks. Everything else in the API is an action performed on one of these.

EntityHoldsWho can see it
RequestCustomer name/phone, address, item, current stage, assigned riderRetailer who created it, assigned rider, dispatcher
User / RolePhone + password, role: retailer / dispatcher / riderSelf only, via login
QR TokenOne-time proof-of-delivery secret, tied to a requestNever exposed publicly — only decoded from the generated image
Tracking CodePublic-safe reference for a request, no internal IDs attachedAnyone with the code — zero login required
